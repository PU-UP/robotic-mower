# 仓库职责与工作约定

2026-10-30。当前定位：机器人软件与算法的架构设计、讨论、实现核对和演进待办仓库，侧重算法。rlcp 是首款实际产品，roboframe 是持续维护的参考架构及其实现。当前不管理两者的指定版本，不建立子模块，也不承担产品代码修改、构建或发布。

## 负责什么

| 职责 | 需要留下的内容 | 边界 |
| --- | --- | --- |
| 架构设计 | 算法能力与协作、输入输出、数据所有权、业务与执行边界、运行约束 | 不复制代码仓库中的详细 API、配置和实现说明 |
| 方案讨论与决策 | 要解决的问题、约束、选项、取舍理由、结论和未决问题 | 讨论中的建议不自动变成产品需求；结论得到确认后才更新当前设计 |
| 产品与参考架构对照 | rlcp 当前怎样做、参考架构怎样设计、差异是否有必要调整 | 差异本身不是缺陷，不要求产品逐项照搬参考架构 |
| 实现核对与架构验收 | 对照已明确的要求读取相关实现，记录符合项、差异、证据和限制 | 只读核对；不能凭目录、类名或设计文档就声称能力已实现 |
| TODO 记录与跟进 | 来自需求、想法、代码观察或验收差异的下一步，附完成条件 | 不因列入 TODO 自动修改外部仓库，不作为人员排期系统 |

优先关注感知、定位、规划控制等算法的能力、数据流和协作边界，也覆盖相关业务决策；算法方案和效果权衡可按具体议题展开。硬件、通信、监控、App 等只在影响这些能力的接口与职责时纳入讨论，不扩展成全公司软件与组织管理。

## 资料的权威范围

- 参考架构文档表达设计方向；rlcp 代码表达某次查看时的实现，两者都不能替代经确认的产品需求。
- 一次代码观察、一次测试结果和实机表现是不同证据，记录时分别说明。代码现状不是必须保留的要求，设计意图也不是已经实现的事实。
- 对外部仓库只保存角色、工作区路径和必要的源码相对路径，不镜像源码或同步其全部文档。
- 核对时记录日期、查看范围和关键路径；现有提交号可以作为观察证据，但不是依赖锁定，也不要求先指定版本才能讨论。
- 外部实现会变化；旧核对结论保留当时范围，再次用于决策时按需复核，不承诺持续与最新代码同步。

## 最小工作流程

问题或想法 → 写清目标与约束 → 讨论并确认设计 → 按需核对实现 → 记录差异与 TODO → 按完成条件复核。

无需每个议题走完全部步骤。小问题直接记录在 TODO；需要比较方案或解释取舍时，再建一份主题文档。出现需要落地的改动，只在这里描述目标、影响仓库和验收条件；实施由对应代码仓库中的任务承担。

长期有效的结论写回系统或参考架构文档。主题记录保留理由和链接，TODO 保留下一步，避免三处重复维护同一份设计。新结论替代旧结论时注明原因；历史资料不并列为当前要求。

## 核对与验收逐步定义

具体要求如何确认、采用什么证据验收、哪些结论属于产品特例或应反馈到参考架构，留到后续使用和实际议题中逐步定义。当前不建立固定验收模板、必填字段或统一门槛，也不把制定这些规则作为开展讨论的前置任务。

先保持基本约定：记录实际查看或验证的范围与依据，区分设计意图、代码观察和运行结果；只读过代码就不声称功能已经通过运行验收。证据不足或需求未明确时直接注明，必要时进入 TODO。

## 必备的文件组织

| 文件 | 唯一用途 |
| --- | --- |
| 根目录 `README.md` | 仓库定位、外部仓库角色与路径、阅读导航 |
| 本文 | 职责边界、记录方式和验收措辞 |
| `docs/RLCP_BASELINE.md` | 首款产品的架构现状与差异摘要，注明观察范围 |
| `SYSTEM_DESIGN.md`、`docs/ROBOFRAME_ARCHITECTURE_BASELINE.md` | 持续维护的系统与算法参考设计 |
| 根目录 `TODO.md` | 当前待讨论、待核对、待落地或待验收事项的单一入口 |
| `docs/history/` 及已标记的历史实验文档 | 设计演进与旧实验追溯 |

有实际议题时再在 `docs/` 下增加主题文档，设计讨论、实现核对和结论可以先放在同一份文档。现在不预建 decisions、reviews、acceptance 等空目录，不增加数据库、自动同步、总构建脚本或模板系统。

## 当前不承担及以后再决定的事项

不修改 rlcp/roboframe 代码，不管理版本组合、依赖、发布和部署，不在这里重建 Brain、算法替身或测试执行框架。子模块与统一开发工作区已退出当前规划；实际有需求时再讨论。

`Brain` / `business_core` 的名称和边界属于待设计事项。先定义职责与输入输出，再决定名称；不因旧原型已退役而预设必须新增或拆出一个模块。
